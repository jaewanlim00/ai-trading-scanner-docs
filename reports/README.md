# 작업 결과 보고서 규칙

각 작업 완료 후 `reports/YYYY-MM-DD-short-topic.md` 형식으로 보고서를 작성한다. 날짜는 작업 기준일이며, 파일명은 짧은 영문 kebab-case로 쓴다. 기존 보고서는 수정하거나 덮어쓰지 않는다.

## 필수 항목

- 작업명과 날짜
- 요청 목적 및 승인된 범위
- 변경 파일 목록과 파일별 핵심 내용
- 보존한 기존 변경 사항 또는 영향받은 기존 기능
- 빌드·테스트·실행 결과: 실행 명령, 성공 여부, 필요한 핵심 출력
- 검증하지 못한 항목과 이유
- 보안 및 운영상 미해결 사항
- 다음 작업과 승인이 필요한 항목
- 관련 설계 결정 또는 handover 문서 링크

## 작성 원칙

- 사실과 관찰 결과를 구분하고, 실행하지 않은 검증은 성공으로 표시하지 않는다.
- 오류가 있었다면 원인, 조치, 재검증 결과를 기록한다.
- API 키, 토큰, 비밀번호, `.env.local`, Supabase Service Role Key 등 비밀값은 절대 기록하지 않는다. 환경변수는 이름과 설정 여부만 기록한다.
- 일반 텍스트 Markdown으로 작성하고, 기존 보고서를 고치기보다 새 보고서를 추가한다.
