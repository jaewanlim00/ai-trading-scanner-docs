## 이번 단계 허용 범위
읽기 전용 코드 분석과 설계 문서 작성만 허용한다. 다음을 조사한다.
1. 네 분석 API(start/step/status/results)의 현재 호출 흐름과 보호 필요 지점
2. 현재 프로젝트에 인증·세션·사용자 식별 기능이 있는지
3. 이 앱을 단일 사용자 전용으로 안전하게 제한하는 현실적인 인증 방안과, 추후 다중 사용자 확장 방안
4. run 소유권을 어떤 방식으로 저장·검증해야 하는지
5. 시작/step 요청의 rate limit을 서버리스 환경에서 일관되게 적용할 방안
6. task attempts 상한, lease 만료, stale task 종료, 수동 재시도 및 run 상태 복구 정책
7. 인증 도입 시 필요한 환경변수 이름만 제안하고 실제 값은 읽거나 출력하지 않는다.
8. 필요한 코드 파일, DB 변경 여부, 외부 서비스 설정 여부, 테스트 계획과 위험을 정리한다.

## 금지 사항
- 소스 코드나 SQL 파일 수정 금지
- Supabase 대시보드/원격 DB 접속 및 변경 금지
- migration 실행 또는 수정 금지
- 환경변수·API 키·비밀값 생성, 변경, 출력 금지
- 패키지 설치/제거 및 버전 변경 금지
- 배포 및 외부 서비스 설정 변경 금지

## 설계 원칙
- 공개 배포 전 인증 없는 분석 API 호출을 차단해야 한다.
- service role은 서버 전용으로 유지하고 RLS만으로 API 인증을 대체하지 않는다.
- runId만으로 타인의 run을 조회하거나 step 실행할 수 없어야 한다.
- Vercel 다중 인스턴스에서도 유효한 rate limit이어야 한다. 인스턴스 메모리만 사용하는 방식은 최종안으로 제안하지 않는다.
- 작업 재시도는 무한 반복되지 않아야 하며, 일시적 실패와 영구 실패를 구분한다.
- 사용자가 승인하지 않은 외부 서비스/유료 서비스 추가를 전제로 하지 않는다.
- 인증 방식은 기존 코드와 배포 환경에 가장 적합한 방안을 우선 제안하고 대안을 비교한다.
